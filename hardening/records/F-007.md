# Challenge record — F-007: destructuring `let` left a stale implicit value

```text
Challenge:                  flow-cursor-rules twin `destructure-then-bare` (semantic.ts)
Source/paper:               —  (§6 implicit flow)
TENSA features stressed:     implicit flow / cursor (§6), tuples
Expected semantics:         the implicit value is the most recent statement's value;
                            after `let (a, b) = Two(x)` that value is a tuple, so a
                            following bare op has no single tensor to consume
TENSA implementation:
    dim B
    model Two(x: Tensor[B, 16]) -> (Tensor[B, 8], Tensor[B, 4]) { … }
    model M(x: Tensor[B, 16]) -> Tensor[B, 8] {
      let (a, b) = Two(x)
      linear(8)
    }
Check result (before):      ok — `linear(8)` silently consumed `x` (the cursor from
                            before the `let`), i.e. the tuple statement was invisible
                            to the flow rule while a single `let` was not
Check result (after):       AXS0408 at line 8: "expected a tensor value here, found tuple"
                            (same code and message as an inline tuple expression)
Finding classification:     F (rule applied inconsistently between the two `let` forms)
Severity:                   major — silently wires the wrong tensor
Proposed action:            DONE — destructuring `let` sets the cursor to the tuple
Language change required?:  no — the documented rule was already "most recent value"
Regression test added?:     yes — twin destructure-then-bare (and tuple-then-bare)
```

Related: E-003 — a side `let` of an unrelated value also redirects the cursor
(`let s = mean(x, axis: 0)` followed by a bare `gelu` continues from `s`). That
is the rule working as documented, but it is surprising; recorded as a design
note, not fixed (see twin `let-redirects-cursor`, which pins the current behaviour).
