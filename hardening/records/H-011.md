# H-011 — device placement: GPU when available, CPU otherwise

Challenge: all emitted M4 programs (2026-09-18).
Source/paper: execution policy, not an architecture.
TENSA features stressed: existing plan `device` setting, model/state allocation, constants, masks and batch transfer.
Expected semantics: generated PyTorch runs on CUDA, then MPS, when one is available and on CPU otherwise; an explicit device (`device cpu` in the plan, `device="cpu"`/`"cuda"` at the generated entry points, `--device` in the harness) is honoured as given.
TENSA implementation: generated `execution_device` chooses CUDA, then MPS, then CPU. Parameters/buffers initialise on the target; graph constants/masks use the local device; training and validation batches move recursively (`move_batch`). A non-persistent anchor supports parameterless modules and later `module.to()`. Host-owned models passed through `models=` (H-010) are moved to the plan's device.
Check result: source language unchanged; `device` remains plan metadata.
Inspect result: device policy visible when specified.
IR result: no new device ops in model graphs.
Runtime result: the reference interpreter is a CPU-only validation oracle (CLI/UI/docs labels), never evidence of a GPU run.
Reference result: torch 2.11.0+cu128, RTX 4090: nine compiling challenges, thirteen graphs, seven plans on GPU against the CPU oracle. torch 2.12 CPU-only: the same gate passes with the automatic CPU selection. MPS selection is implemented but not hardware-tested.
Gradient result: GPU parameter gradients compared to the CPU oracle.
Diagnostics: none; no new AXS code.
Finding classification: H, fixed.
Severity: major (device placement was absent).
Workaround: none needed.
Proposed action: retain hardening/validate-m4.{ts,py} as the fidelity gate; mixed precision remains an unsupported annotation.
Language change required?: no.
Regression test added?: backend H-011 (selection order, explicit `device cpu`, batch transfer).

Decision (2026-09-18): an earlier draft of this fix made a missing GPU a hard error ("no CPU
fallback"). Reverted before merge — a generated program must run wherever PyTorch runs; the
device is a deployment fact, not a correctness property the language should refuse on.
