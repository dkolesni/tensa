# Challenge record — F-021: a field pipeline could not refer to an earlier field by name

```text
Challenge:                  lm-padded (fields `padded` → `pad`; `ids` → `inputs`/`targets`)
Source/paper:               next-token LM with padding (§20 data plane)
TENSA features stressed:     `data … example { field … }` pipelines built from other
                            fields (shifted targets, a mask sliced from a padded row)
TENSA implementation:
    example {
      field padded: Mask[1, T + 1] = tokenize(text, vocab: V) |> pad_mask(T + 1)
      field pad:    Mask[1, T]     = padded[0 : 1, 0 : T]
      field ids:    Tokens[T + 1]  = tokenize(text, vocab: V) |> pad_to(T + 1)
      field inputs: Tokens[T]      = ids[0 : T]
      field targets: Tokens[T]     = ids[1 : T + 1]
    }
Check result (before):      AXS0204 "unknown data operation 'padded'" (and 'ids'). A bare
                            name at the head of a field pipeline was looked up in the
                            DATA-OP catalog, not among the fields declared so far. The
                            bundled gpt example only got away with `window` because a
                            data op happens to be called `window` — a coincidence, not
                            a rule.
Check result (after):       a name that matches a field declared EARLIER in the same
                            example lowers to pipeline op `field.<name>`; the field's
                            declared type is the contract (the pipeline's `reshape`/
                            `kindOut` metadata is documentary). Names that match nothing
                            still warn AXS0204 (tests.ts: `missing` warns, `ids` does not).
Runtime result:             the runtime synthesises one tensor per field NAME, so
                            `inputs` and `targets` are consistent within a step
                            (H-007's field cache).
Reference result:           emitted plan derives the batch dict per field; `field.x`
                            ops read `batch["x"]`.
Finding classification:     F (the data plane's own scoping rule was missing — an
                            example is a sequence of bindings, like a model body)
Severity:                   major — the canonical LM input/target pair was unwritable
                            without an accidental op-name collision
Workaround:                 name the intermediate after a data op (!)
Proposed action:            DONE — `analyze.ts` `dataPipeline(...)` takes the map of
                            earlier fields; the field loop calls it before recording the
                            new field's type, so a field cannot refer to itself or to a
                            later one.
Language change required?:  no (the grammar already allowed the expression)
Regression test added?:     yes — `data / a field may be built from the fields declared
                            before it, whatever its name (F-021)`; challenge `lm-padded`
```
