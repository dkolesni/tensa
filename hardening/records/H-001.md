# Challenge record — H-001: the reference runtime ignored schedules, `until` and events

```text
Challenge:                  baseline-ceremony, curriculum-events, transfer-lifecycle,
                            distillation (every M3 lifecycle challenge); ledger H-001
                            was opened in Milestone 1 as "known, not scheduled"
Source/paper:               §22 lifecycle simulation, §26 escalation ladder
TENSA features stressed:     `cosine(warmup:)` / `linear(warmup:)` schedules,
                            `until <metric> <cmp> <value>`, `every N steps|epochs
                            { validate ; checkpoint }`, per-phase `lr` overrides,
                            `clip_grad`, `track … = ema(...)`
TENSA implementation:        (curriculum-events)
    phase easy { epochs 10  until main < 0.9  update main with opt }
    phase hard { steps 6  linear(warmup: 2)  update main with opt
                 every 3 steps { validate } }
    every 5 steps { checkpoint }
Runtime result (before):    `exec.ts` ran each phase for its step/epoch budget and
                            stepped the optimizers at a fixed learning rate. Schedules,
                            `until`, events, lr overrides and `clip_grad` were stored in
                            the IR and reported by `inspect`, but a `run` could not tell
                            you whether a stopping rule ever fired or an lr override
                            applied to the right region. The M3 challenges needed
                            exactly that evidence, so this became blocking.
Runtime result (after):     the training loop simulates the whole plan:
                              · one epoch = `STEPS_PER_EPOCH` (6) synthetic steps
                              · schedules multiply the lr per step (warmup, cosine /
                                linear decay over the phase budget)
                              · region lr overrides and freezes are honoured per phase
                              · `until` is evaluated on the step's loss metrics
                                (`<loss>`, `train_<loss>`, `val_<loss>`) and ends the
                                phase
                              · events fire on their counters (H-008) and are recorded
                              · `clip_grad` scales gradients before the step
                              · `track … = ema(...)` shadows are updated after each step
                            and the RunReport gained `phases[{name, steps, stoppedBy:
                            "epochs"|"steps"|"until"|"maxSteps", lrStart, lrEnd}]` and
                            `events[{step, phase, action, detail}]`.
Reference result:           the emitted plan does the same with `apply_schedule`
                            (LambdaLR-style multiplier), `set_lr` per param group,
                            `until` → `break`, event hooks, `clip_grad_norm_`; the 16
                            learning programs were executed under torch 2.12 CPU.
Finding classification:     H (backend/runtime gap; the language already said it)
Severity:                   major once M3 depended on it
Proposed action:            DONE — `exec.ts` training loop rewrite; `emit_torch.ts`
                            `emitPlan`.
Language change required?:  no
Regression test added?:     yes — `lifecycle / plan-level events count run steps, phase
                            events count phase steps; `until` ends a phase (H-001,
                            H-008)`; challenges `baseline-ceremony`, `curriculum-events`,
                            `transfer-lifecycle`, `distillation` (run checks on
                            `report.phases` / `report.events`)
```
