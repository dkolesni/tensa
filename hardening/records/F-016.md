# Challenge record — F-016: a `fn` application was `pure` whatever its body did

```text
Challenge:                  fn-effects
Source/paper:               —  (§15 effects; §21 "`augment(x)` twice is two draws")
TENSA features stressed:     `fn` (parameter-free reusable block), effect tracking,
                            `dropout` / `batchnorm` / `stop_grad` inside a fn
TENSA implementation:
    fn noisy(x: Tensor[B, D]) -> Tensor[B, D] { return x |> dropout(0.1) }
    fn normed(x: Tensor[B, D]) -> Tensor[B, D] { return x |> batchnorm }
    fn stopped(x: Tensor[B, D]) -> Tensor[B, D] { return stop_grad(x) }
    fn clean(x: Tensor[B, D]) -> Tensor[B, D] { return x * 2.0 }
    model M(x: Tensor[B, D]) -> Tensor[B, D] {
      let a = noisy(x)  let b = normed(a)  let c = stopped(b)  let d = clean(c)
      return d |> linear(D)
    }
Check result (before):      ok. The `apply` node for each fn was created with the default
                            effect list `["pure"]`; only the nodes INSIDE its region knew
                            they were stochastic / stateful / grad-stopped. Anything that
                            reads the top level of a graph — the inspect effects table,
                            the eval-pipeline "stochastic" check, the contrastive-views
                            "two draws" reasoning — saw a pure model.
Check result (after):       every node that owns regions (apply, residual, parallel,
                            scan, static_repeat) carries the union of its body's
                            effects: noisy → stochastic, normed → writes-state,
                            stopped → grad-stopped, clean → pure. The module effect set
                            is {stochastic, writes-state, grad-stopped}.
Runtime result:             unchanged (the runtime always executed the bodies); what
                            changed is what the language SAYS about the call.
Reference result:           PyTorch has no such summary; a module's `training` flag is
                            the only hint that dropout is somewhere inside.
Finding classification:     F (effect tracking was not compositional)
Severity:                   major — an eval pipeline could call a stochastic fn and
                            pass the "no randomness at eval" check
Workaround:                 inline the fn body
Proposed action:            DONE — `analyze.ts` `node()` computes the union when
                            `opts.regions` is given and no explicit effects are passed;
                            `inspect.ts` reads container effects the same way.
Language change required?:  no
Regression test added?:     yes — challenge `fn-effects` (`effects` expectation + custom
                            per-application check)
```
